# MOLIVE 디자인 다양성 — 1차 수정 계획 (범위 축소 · 결정적 반영 우선)

## Context

업종이 다른 3개 브리프(아기용품 / 인테리어 / 식품) 결과가 동일한 split Hero, 동일한 editorial 시퀀스,
동일한 neutral/beige 팔레트로 수렴한다. 사용자가 지정한 brand main color도 최종 화면에 거의 남지 않는다.

코드 추적 결과 원인은 두 가지다.

1. **brand color가 두 지점에서 끊긴다.**
   `pagePlanSchema`에 색 필드가 없어 1단계에서 hex가 소실되고(2단계가 따르는 `renderPagePlanContract`에 색이 한 글자도 실리지 않음),
   `commerce.accent`는 스키마가 필수로 받아 저장까지 하지만 **소비하는 렌더러가 코드베이스에 0곳**이다.

2. **섹션 변주 축이 4개뿐이라 레이아웃이 붕괴한다.**
   `alignment / mediaPosition / density / tone`만으로는 `imageText` · `brandStory` · `productFocus` · `materials`가
   전부 "반은 사진, 반은 카피"로 같아진다. 레퍼런스가 이들을 구분하는 **컨테이너 폭 · 컬럼 수 · 표면 표현**이 스키마에 없다.

목표 두 가지는 유지한다: **입력 hex가 최종 디자인에 확실히 반영될 것**, **업종이 다르면 구조가 육안으로 다를 것**.

**설계 원칙: AI 준수에 기대지 않는다.**
plan이 정한 값은 코드가 생성 HTML에 속성으로 주입하고, 코드 소유 baseline CSS가 소비한다.
AI가 축을 무시해도 최소한의 geometry·색 차이는 반드시 나타난다. **retry validator는 하나도 추가하지 않는다.**

## 각 수정의 정확한 목적

**A — hex가 1단계에서 소실되지 않게 한다.**
`renderPagePlanContract` 텍스트에 "이 브랜드의 색은 X, 전략은 Y"가 실린다. 현재는 색이 전혀 없어 2단계가 무드로 재해석한다.

**B — hex를 검증하지 않고 확정한다.**
사용자가 hex를 넣었으면 코드가 `plan.palette.brandColor`와 `source.commerce.accent`를 그 값으로 덮어쓴다.
위반 → 재생성 경로를 만들지 않는다.

**C — 섹션이 같은 모양으로 붕괴하는 것을 막는다.**
컨테이너 폭 / 컬럼 수 / 표면 표현이 축으로 존재해야 `imageText`와 `brandStory`가 다르게 시공된다.

**D — plan 값을 DOM에 못 박는다.** ← *"AI가 무시해도"에 대한 답*
AI에게 속성을 붙이라고 지시하는 대신, **생성 직후 코드가 HTML을 후처리해 속성을 주입**한다.
`data-moire-tone`도 여기서 주입한다(AI 의존 제거).

**E — 주입된 속성이 실제 픽셀이 되게 한다.**
코드 소유 baseline CSS가 container/tone/surface를 소비한다. AI CSS 뒤에 emit되어 동률 명시도에서 코드가 이긴다.

**F — 색이 반드시 면적으로 남되, 모든 페이지가 같아지지 않게 한다.**
본문에 accent 밴드를 최소 1개 보장하고, 푸터 brand 적용은 `colorStrategy`에 따라 달라진다.

**G — Hero 수렴을 끊는다.**
`full-bleed` / `split-editorial` / `cinematic-still` spec이 모두 "큰 이미지 + eyebrow + 대형 타이틀 + CTA 1개"로 읽혀
planner가 사실상 한 종류만 고른다(3개 결과 전부 split-editorial).
카피 앵커 · 오버레이 유무 · 뷰포트 비율 · 하단 연결부를 서로 배타적으로 다시 쓴다.
`banner-stack` / `product-forward` spec의 평가절하 어휘도 제거한다.

**H — 레지스트리가 중립 톤을 문법으로 규정하는 것을 푼다.**
spec에 "저채도", "잡지 지면처럼", "톤을 눌러", "정숙한", "여백이 디자인의 절반"이 반복되고
`IMAGE_TREATMENTS.desaturated-editorial`이 fashion/interior/lifestyle 3업종의 첫 후보다.

**I — 레퍼런스의 지배 패턴 복원.**
ubona · PURE BLANC · ToolBox · ART STORE · PROPET · AUREL 다수가 Hero 직후 카테고리 퀵메뉴를 둔다.

## D. plan 값을 section DOM에 결정적으로 주입

신규 `lib/design-library/plan-attributes.ts` — `applyPagePlanAttributes(html, plan): string`.
`site-generator.ts`에서 `ensureEditingMetadata` 직후에 실행한다(기존 후처리 파이프라인과 동일한 자리).

**매핑 규칙 — 직접 매칭 우선, 순서는 fallback**
단순 occurrence 순서는 AI가 섹션을 하나 더/덜 만들면 전체가 밀린다. 따라서 **확정적인 신호부터 소진**한다.
각 pass에서 매칭된 요소와 plan 섹션은 pool에서 제거한 뒤 다음 pass로 넘어간다.

| pass | 근거 | 대상 |
|---|---|---|
| 1 | `data-moire-id` / `data-moire-plan` 값이 plan 섹션 `id`와 **정확히 일치** | 있으면 그대로 확정 |
| 2 | `data-moire-type="hero"` | `plan.hero` |
| 3 | `data-cafe24-slot="product-list"`를 포함한 최상위 `<section>` | plan의 `featuredProducts` (슬롯은 검증상 정확히 1개라 항상 성립) |
| 4 | `data-moire-type` 의미 매칭 (`products` / `footer` 등 고유 타입) | 해당 역할의 plan 섹션 |
| 5 | **fallback** — pass 3의 상품 섹션을 앵커로, 남은 `<section>`을 앞/뒤로 나눠 남은 plan 섹션과 **각 끝에서부터** 순서 정렬 | 나머지 |

개수가 맞지 않아 남는 `<section>`에는 아무 속성도 붙이지 않는다(무해하게 통과).
매칭 결과는 `planAudit.attributeMapping: { byId, byType, byAnchor, unmatched }`로 trace에 남겨,
fallback 의존도를 관측하고 2차의 `columns` 강제화 판단 근거로 쓴다.

**주입 속성**
```html
<section data-moire-plan="brand-story-2"
         data-moire-tone="accent"
         data-moire-container="full-bleed"
         data-moire-columns="3"
         data-moire-surface="card"> …
```
- `data-moire-id` / `data-moire-type`과 같은 성격의 편집 메타 속성이므로 기존 편집기·보호 검사와 충돌하지 않는다.
- 저장 HTML에 남으므로 Preview · Cafe24 export · 재편집에서 동일하게 유지된다.
- **AI에게 이 속성을 붙이라고 지시하지 않는다.** 계약 텍스트에는 축의 *의도*만 싣고, 속성은 코드가 붙인다.

## E. 주입 속성을 소비하는 baseline CSS

신규 `lib/design-library/plan-layout-css.ts` — `planLayoutCss(plan)`.
`preview-document.ts`와 `theme-package.ts`에서 **AI CSS 뒤**에 emit한다(동률 명시도에서 코드가 이김).

### 강제되는 축 (AI가 무시해도 반드시 나타남)

**`container` — 최소 geometry 차이 보장**
inline measure만 건드린다. 수직 리듬 · display · grid는 손대지 않아 레이아웃이 깨질 경로를 막는다.
```
[data-moire-root] [data-moire-container="boxed"]      {padding-inline:max(24px,calc((100% - 1200px)/2))}
[data-moire-root] [data-moire-container="wide"]       {padding-inline:max(24px,calc((100% - 1560px)/2))}
[data-moire-root] [data-moire-container="asymmetric"] {padding-inline:clamp(24px,9vw,200px) clamp(24px,3vw,56px)}
[data-moire-root] [data-moire-container="full-bleed"],
[data-moire-root] [data-moire-container="full-bleed"] > *{max-width:none;margin-inline:0}
[data-moire-root] [data-moire-container="full-bleed"] {padding-inline:0}
```
`full-bleed`만 직계 자식까지 내려가 AI의 내부 래퍼 max-width를 푼다(그래야 실제로 전폭이 된다).
나머지는 섹션 자체 padding만 조절하므로 AI 내부 컨테이너와 더해져도 폭이 좁아질 뿐 깨지지 않는다.

**`surfaceStyle` — 표면 표현 차이 보장**
```
[data-moire-root] [data-moire-surface="outlined"]{border-block:1px solid var(--molive-line)}
[data-moire-root] [data-moire-surface="card"] > *{background-color:var(--molive-raised);border-radius:var(--molive-radius)}
```
`flat`은 규칙 없음. `photoField`는 사진 자산이 필요하므로 **advisory**(계약 텍스트로만 전달).

**`tone` — 배경 밴드**
`accent`만 **전체 명시도**로 강제한다(F의 brand 면적 보장과 직결).
`light` / `tinted` / `dark`는 `:where()`로 명시도 0의 **폴백**이라, AI가 그 섹션 배경을 직접 디자인했으면 AI가 이긴다.

**반드시 `background` 축약형이 아니라 `background-color`를 쓴다.**
축약형은 `background-image`를 `none`으로 초기화하므로, AI가 그 섹션에 깔아 둔 사진·그라디언트를 지워 버린다.
`background-color`만 쓰면 이미지가 있는 섹션에서는 색이 이미지 뒤에 깔릴 뿐이라 손실이 없다.
```
[data-moire-root] [data-moire-tone="accent"]{background-color:var(--molive-brand);color:var(--molive-brand-on)}
[data-moire-root] :where([data-moire-tone="tinted"]){background-color:var(--molive-brand-tint)}
[data-moire-root] :where([data-moire-tone="dark"])  {background-color:var(--molive-neutral-ink);color:var(--molive-neutral-ink-on)}
```
`color`도 accent에서만 강제한다. 이미지 위 텍스트 대비는 AI가 오버레이로 이미 처리했을 수 있으므로,
`background-image`가 선언된 섹션까지 텍스트 색을 뒤집지 않도록 `color`는 accent 한 값에만 건다.

### advisory 축 (custom property + 계약 텍스트만)

**`columns`** — 카드 컨테이너는 섹션의 임의 깊이 자손이라 코드가 결정적으로 도달할 수 없다.
코드는 섹션에 `--molive-columns:N`을 선언하고, 계약이 `repeat(var(--molive-columns),1fr)` 사용을 지시한다.
강제하지 않는다. (컬럼 강제는 2차에서 D의 매핑 신뢰도를 측정한 뒤 재검토)

## F. brand color 반영 정책

신규 `lib/commerce/brand-theme.ts` — 입력 hex 하나에서 결정적으로 램프를 만든다.

**1) CSS 변수 — 전용 namespace, Header 오염 불가 구조**

기존 코드가 이미 `--moire-` namespace를 쓰고 있다(확인된 것: `--moire-card-font/gap/min/pad/radius`,
`--moire-thumb-bg/fit/ratio`, `--moire-header-gap`, `--moire-icon-size`, `--moire-footer-ink`,
`--moire-footer-icon-filter`). 이름이 겹치지 않더라도 같은 namespace에 색 토큰을 섞으면
Header·상품 카드 토큰과 구분이 흐려진다. → **brand 전용 `--molive-` prefix로 분리한다.**

```
[data-moire-root]{                      /* :root · html · body 에는 절대 선언하지 않는다 */
  --molive-brand: #hex
  --molive-brand-strong / --molive-brand-tint / --molive-brand-soft
  --molive-brand-secondary                     (duotone 전용, 3)에서 파생)
  --molive-brand-on:      (hex 위 텍스트 — WCAG 대비로 흑/백 결정)
  --molive-neutral-ink / --molive-neutral-ink-on / --molive-line / --molive-raised / --molive-radius
}
```

**Header 간접 변경이 구조적으로 불가능한 이유 (검증 완료)**
`composeCommerce`는 `\`${header}${html}\``로 Header를 AI 루트의 **형제**로 앞에 붙이고,
Preview는 `includeHeader:false`로 아예 분리 렌더한다. 즉 `#header.pocHeader`는
`[data-moire-root]`의 자손이 아니므로 위 변수가 **상속될 경로가 없다.**
이 보장은 "`:root` / `html` / `body`에 선언하지 않는다"가 지켜질 때만 성립하므로 테스트로 고정한다.

**푸터도 같은 이유로 변수를 못 받는다.** `footer#footer`는 AI 루트 밖의 최상위 요소다.
따라서 3)의 푸터 분기는 `var()` 참조가 아니라 **JS에서 계산한 리터럴 hex**를 emit한다.

계약에는 "색은 리터럴 hex 대신 `var(--molive-brand)` 계열을 쓴다"를 넣는다. 사후 색 교체가 한 값 변경이 된다.

**2) 본문 accent 밴드 최소 1개 보장 — 획일화 없이 색을 남기는 핵심**
`normalizePagePlan`에 규칙 추가: 브랜드 색이 있는데 `tone === "accent"`인 본문 섹션이 하나도 없으면,
코드가 후보 중 하나를 승격한다. 후보 우선순위는 `cta` → `editorialBanner` → `promotion` → `categoryGrid` → `gift`
(전환·탐색 역할 섹션, `featuredProducts` 제외). E의 accent 규칙이 전체 명시도이므로
**어떤 결과물이든 본문에 브랜드 색 면적이 최소 1개 존재한다.**

**3) `colorStrategy`가 색의 양을 조절 — 반대 방향 획일화 방지**

| colorStrategy | 본문 accent 밴드 | tinted 밴드 | Footer |
|---|---|---|---|
| `dominant` | 최대 2개까지 승격 | brand-tint | **brand** |
| `band` | 1개 보장 | brand-tint | **brand-tint** |
| `accent-only` | 1개 보장 | 중립(brand 미사용) | `footerMood` 그대로 |
| `duotone` | 1개 보장 | 2차 색 | `footerMood` 그대로 |
| `monochrome` | 승격 안 함 | 중립 | `footerMood` 그대로 |

→ **모든 페이지 푸터를 brand color로 칠하지 않는다.** `dominant` / `band`에서만 푸터가 브랜드를 입고,
나머지는 기존 `FOOTER_MOODS`(ink-dark / paper-light / warm-tinted)를 유지해 푸터 다양성을 지킨다.
`FOOTER_MOODS`에 `brand-block`을 추가하고, `buildFooterThemeCss`가 위 표대로 분기하되
`footer#footer`는 AI 루트 밖이므로 **계산된 리터럴 hex**를 쓴다.

**3-1) `duotone`의 secondary color — 코드가 결정적으로 파생 (신규 사용자 입력 없음)**
1차에서는 색 입력을 늘리지 않고 `brandColor` 하나에서 파생한다. `brand-theme.ts`에 순수 함수로 둔다.
```
secondary = fromHsl(
  h: (brandH + 150) mod 360,          // 보색(180°)은 진동이 심해 150° 스플릿 보색을 쓴다
  s: clamp(brandS * 0.85, 0.18, 0.72), // 채도를 살짝 낮춰 본색이 주인공 자리를 지키게 한다
  l: clamp(brandL,        0.38, 0.62)  // 밴드 배경으로 쓸 수 있는 명도 구간으로 정규화
)
```
- 무채색 입력(`s < 0.08`)이면 hue 회전이 무의미하므로 secondary는 명도만 벌린 중성색으로 파생한다.
- `duotone`에서 `tinted` 밴드가 `--molive-brand-secondary`의 tint를 쓰고, `accent` 밴드는 본색을 유지한다.
- 사용자 지정 secondary 입력은 2차 항목으로 남긴다.

**3-2) `monochrome` 오용 방지 — 명시 hex가 색을 다시 잃지 않게**
사용자가 hex를 명시했는데 AI가 `colorStrategy: "monochrome"`을 고르면 B·F가 확보한 색이 도로 사라진다.
`normalizePagePlan`에서 결정적으로 막는다(재시도 아님).
```
if (userSuppliedHex && plan.palette.colorStrategy === "monochrome" && !briefAsksMonochrome(prompt))
    plan.palette.colorStrategy = "accent-only";   // 색을 남기는 가장 절제된 전략
```
- `briefAsksMonochrome`은 `inferIndustry`와 같은 방식의 결정적 키워드 검사다
  (`모노크롬` · `무채색` · `흑백` · `블랙앤화이트` · `monochrome` · `black and white` · `그레이스케일`).
  **사용자가 브리프에서 명시적으로 요구한 경우만 예외**로 통과시킨다.
- hex를 입력하지 않은 경우에는 AI가 `monochrome`을 포함해 어떤 전략이든 자유롭게 고를 수 있다.
- 같은 이유로 `surfaceFamily`도, hex가 있는데 `dominant`인데 `surfaceFamily: "white"`처럼
  색을 무력화하는 조합이 오면 `tinted`로 눌러 준다.

**4) Header — 변경 없음**
`commerceCss`는 지금처럼 `surface / ink / fontFamily`만 쓴다. `headerTextTone` 상속 구조 동결.

**5) Preview와 Export 동일 주입**
`preview-document.ts:65`의 CSS 조립과 `theme-package.ts:95`의 `protectedCss` 양쪽에
`brandThemeCss(...)` + `planLayoutCss(...)`를 같은 위치(AI CSS 뒤)로 넣어 Preview = Cafe24를 보장한다.

**6) 관측만 하는 지표 (재시도 없음)**
`planAudit`에 `brandColorUsage: { declaredInAiCss, appliedByRenderer, accentSections }`를 남긴다. **validator가 아니다.**

## 구조 다양성을 실제로 늘리는 variation axis (C)

`pagePlanSectionSchema` / `pagePlanJsonSchema`에 추가하고, `SECTION_*_SPECS`와 같은 한국어 spec 사전을 만들어
`axisLine()`이 계약 텍스트에 함께 싣는다.

| 축 | 값 | 강제 여부 | 레퍼런스 근거 |
|---|---|---|---|
| `container` | `boxed` / `wide` / `full-bleed` / `asymmetric` | **강제** | ToolBox 좌라벨+우상품행, goods-2 쿼드런트, fashion-1 풀폭 색면 |
| `surfaceStyle` | `flat` / `card` / `outlined` / `photoField` | `photoField`만 advisory | puppy 색 타일 카드, PURE BLANC 파스텔 카드 |
| `columns` | `1`~`6` | advisory | ART STORE 5열, children-3 2열, 6열 모자이크 |

`SectionTypeDefinition.axes`에 세 축을 추가하고 `normalizeSection`이 타입별 허용 조합을 눌러 준다.
예: `benefits`는 columns 3~4 · surface outlined|flat, `lookbook`은 container full-bleed 우선,
`featuredProducts`는 container만 반응하고 columns는 `productPresentation`이 소유(중복 방지).
`plan-composer.ts`(대비 경로)도 같은 축을 조합해 AI 없이도 다양성이 나오게 한다.

## 검증 기준

**결정적 검증 (AI 호출 없음)**
```bash
npm test
```
- `brandThemeCss("#0044ff")`에 `--molive-brand:#0044ff`가 있고, `--molive-brand-on`이 대비 규칙대로 흑/백을 고르는지

- **Header 불변**: `brandThemeCss` 적용 전후로 `commerceCss` 출력이 바이트 단위로 동일한지
- 사용자 hex 입력 시 `plan.palette.brandColor` · `source.commerce.accent`가 그 값과 정확히 일치
- **`deriveSecondary`**: 같은 hex는 항상 같은 secondary를 내고, hue가 +150° 회전하며,
  채도·명도가 clamp 범위 안인지 / 무채색 입력(`s<0.08`)에서 중성색 분기를 타는지
- **`applyPagePlanAttributes`**: id 직접 일치가 순서 매칭보다 우선하는지 / hero·product 타입 매칭이 그다음인지 /
